### Bug reproduced

The previous \`detect_scattered_functionality\` treated three or more class names ending in \`Service\`, \`Configuration\` and other broad role suffixes as an alleged scattered concern, regardless of shared functional identity or dependency evidence. In the pinned Java HA run, it produced two unverified medium-severity heuristics.

The revised detector requires a shared non-generic *specific concern stem* across at least three components and at least two different class-role suffixes. It emits a **low-severity, naming-only candidate**, includes matching entity FQNs, and avoids claiming a verified violation or unconditionally recommending centralization. This does not prove that every remaining candidate is a defect.

## Interpretation and known limitations

- **Two fewer Java warnings is a detector-behavior change**, not proof that the Java architecture improved or that both prior warnings were confirmed false positives. The same 327/248/5 graph is recovered from the same target SHA.
- Architecture quality scores driven by smell counts can rise purely because the heuristic changes; **never compare these scores as repository-quality improvement across analyzer versions without qualification**.
- Class-name stems are still only weak semantic evidence; intentional multi-layer concerns may legitimately span components.
- The Python examples result is a *new* target baseline, not a measured before/after FP improvement.
- Parser unsupported-construct coverage and human FP/FN adjudication remain **not evaluated**, not zero.
- Self-analysis using alternate \`wca\` and \`acdc\` algorithms yields different component counts; compare only equal algorithms and configurations.
- Git status + target SHA checks do not fully attest ignored paths, submodules or concurrent file modification. See PR #14 provenance limitations.
- No independent sub-agent audit or human review is claimed. No merge requested.
