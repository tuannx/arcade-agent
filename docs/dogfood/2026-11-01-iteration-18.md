## Finding, scope, and ground truth

`del helper` within a Python function (without a `global` declaration) compiles as a local deletion, not a call to or deletion of the same-module `helper` function. The previous partial call extractor did not mark direct deletion targets as local, so `helper()` after `del helper` was a **potential false call edge**. This is a parser correctness issue, **not** a verified architectural rule violation.

- Minimal regression: `tests/test_parsers/test_python_del_bindings_dogfood.py` (5 tests). Negative labels: bare `del helper`, destructured `del (helper, other)`. Positive controls: `del holder.helper`, `del holder[0]` do not bind `helper`; a deletion inside a nested function does not change its parent's scope. Python call coverage stays `partial`.
- Standalone CPython bytecode experiment, **not the analyzer**: `DELETE_FAST` + `LOAD_FAST_CHECK` for the two local-name cases; `DELETE_ATTR` and `DELETE_SUBSCR` with `LOAD_GLOBAL helper` for the controls. Calling a deleted local raises `UnboundLocalError`.
- Implementation: `_deletion_binding_names` traverses only named deletion-target, tuple/list and expression-list nodes; it does not promote attribute/subscript base names to local bindings.
- No hosted **RED** run was performed against the test-only commit: do not invent two failing tests or claim hosted RED → GREEN. A code inspection of the old extractor plus the bytecode experiment motivated the fix. The five new labels passed in hosted full CI after the fix. Their results do not measure population false-positive rate.
